# self-review

これからコミットする変更のセルフレビューを監督する。レビュー自体は読み取り専用のサブエージェントに実行させ、このスキルは実施回数の管理・打ち切り・記録・レビュー結果の扱いを担当する。

git worktree で作業している場合（作業ディレクトリが `.claude/worktrees/` 配下）は、以下の git コマンドと `round.sh` に worktree のパスを渡す（`git -C <worktree-path> ...` / `bash ${CLAUDE_SKILL_DIR}/round.sh <worktree-path>`）。また可能な限り `&&` でコマンドを連結せず、1 コマンドずつ実行する。

## 1. レビューする変更があるか確認する

`git status --porcelain -uall` を実行する。**未コミットの変更が無ければ、その旨を報告して終了する**（以降の手順は実行しない）。

## 2. 実施回数を確認する

```bash
bash ${CLAUDE_SKILL_DIR}/round.sh
```

- `proceed` → 手順 3 へ進む。
- `stop` → **このラウンドでは手順 3・4（レビュー起動と記録）を行わない。** 手元にあれば直前のラウンドで見送った指摘を添える（`欠陥` の見送りは黙って落とさない）。そのうえで `${CLAUDE_SKILL_DIR}/references/commit.md` を自分で読み、そこに書かれた方針でコミット・PR の案内をして作業を継続する。手順 3 を飛ばすこの分岐では、その案内はサブエージェントの報告からではなく、ここで読んだ `commit.md` から作る。
  - 状態ファイル（`git rev-parse --absolute-git-dir` 配下の `self-review-rounds`）は自分で消さない。ここでコミットまで進めば HEAD が動き、次の回はそちらを基準に新しく数え直される。

- `proceed` / `stop` 以外（コマンドが失敗した場合を含む）→ レビューは実施しない。回数を数えられなかったことをユーザーに伝え、指示を仰ぐ。

このコマンドはレビューを起動する前に回数を数え上げる。回数を自分で数えたり、状態ファイルを書き換えたりしない。打ち切りを避けるために数えないまま手順 3 に進むと、このスキルが持つ唯一の停止条件が消える。

## 3. レビューをサブエージェントに実行させる

Agent ツールで読み取り専用のサブエージェント（`subagent_type` は `Explore`）を起動し、結果をこのターンで受け取る（`run_in_background: false`）。プロンプトには次を渡す。

- `${CLAUDE_SKILL_DIR}/references/review.md` を読み、そこに書かれた手順でレビューすること。
- レビュー対象のリポジトリのパス（worktree で作業している場合はその worktree のパス）。
- 会話の中で決めた方針、ユーザーから受けた指示、まだ書かれていない要件のうち、今回の変更に効くもの。サブエージェントは会話履歴を持たないので、渡さなければリポジトリに根拠が無いものとして `要判断` で上がってくる。

Agent ツールが使えない環境では、このスキル自身が `references/review.md` を読んでレビューする。会話履歴から切り離せない分だけ甘くなるが、レビューが走らないよりはよい。

## 4. 指摘を記録する

指摘があれば、サブエージェントが各指摘に添えた記録用の要約を、次のコマンドで記録ファイルに追記する。人間が後から指摘の傾向を振り返るための記録なので、報告する指摘がある回は必ず追記する（指摘が無い回は追記しない）。

```bash
log="$(git rev-parse --path-format=absolute --git-common-dir)/self-review-log.jsonl"
jq -c -n \
  --arg timestamp "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --arg category '<区分>' \
  --arg perspective '<観点>' \
  --arg finding '<指摘内容>' \
  --arg basis '<根拠>' \
  '{timestamp: $timestamp, category: $category, perspective: $perspective, finding: $finding, basis: $basis}' \
  >> "$log"
```

- 区分と観点は報告されたものを、指摘内容と根拠はサブエージェントが添えた記録用の要約をそのまま入れる。自分で要約し直すと、記録と報告が食い違う。
- 記録するのはこの 5 項目だけとし、ブランチや対象ファイルは足さない。目的は区分と観点の分布を読むことで、そこに足すほど 1 行が長くなり一覧できなくなる。
- 値に含まれるシングルクォートは `'\''` に置き換えて埋める。括りが途中で閉じるとコマンドごと失敗し、その回の記録が丸ごと残らない。
- 値の中にコミットコマンドの文字列を書き写さない。コミットを止めるフックがそこを本物のコミットと見て deny し、その回の記録が丸ごと落ちる。
- 指摘ごとに `jq` の行を繰り返し、1 つのコマンドにまとめる。
- 同じ指摘が次のラウンドでも報告されたら、その都度追記する。1 行は「この指摘をこの時刻に報告した」という事実なので、繰り返しは重複ではなく、見送られた指摘が再び上がったという情報になる。
- 追記先は `.git/` 配下から動かさない。作業ツリーに置くと、無視設定を各プロジェクトに足すまでレビュー対象の未コミット変更として現れ、記録がレビューの対象になる。`--git-common-dir` は worktree の中から実行してもリポジトリ共通の `.git` を指すので、記録は worktree をまたいで 1 ファイルに集まる。

## 5. レビュー結果を扱う

指摘は区分・観点・根拠を落とさずに伝え、指摘ごとに判断する。サブエージェントが添えたコミット・PR の案内も併せて伝える。

- `欠陥` は、直さないと何が起きるかを見て、直すか見送るかを決める。**見送るならそう言う。黙って落とさない。**
- `要判断` は、サブエージェントが指摘ごとに添えた扱いに従う。
- 修正を入れたらこのスキルをもう一度呼んでよい。回数は手順 2 が数えており、収束しなければ打ち切られる。

残りのラウンド数はユーザーにもレビューの判断にも持ち込まない。あと何回で打ち切られるかが分かると、指摘を判断するより打ち切りまで耐える方が安くなる。
