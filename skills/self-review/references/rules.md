# ルール（`.claude/rules/`）レビュー観点

`.claude/rules/` 配下のルールを変更した場合に、共通観点に加算する。frontmatter に `paths` を指定したルールは、それにマッチするファイルを扱ったときだけ読み込まれる。この条件付きの読み込みが、以下の観点の前提になる。

## frontmatter

- `paths` が設定されているか。無いルールは条件によらず読み込まれ、CLAUDE.md と同じくコンテキストを消費し続ける。設定しないことは認めない。
- `paths` の範囲は適切か。効かせたいディレクトリ・ファイルだけが選ばれているか。広すぎると無関係なファイルに触れただけで読み込まれてコンテキストを圧迫し、狭すぎると効かせたい対象で読み込まれない。
- `paths` で指定しているファイルが存在しているか。存在しないパスを指すルールは一度も読み込まれず、書いていないのと同じになる。しかも効いていないことに気付けない。

マッチするかは、パターンを `git ls-files -co --exclude-standard ':(glob)<pattern>'` に渡し、効かせたいファイルが列挙されるかで確認する。`:(glob)` を付けないと git の pathspec では `*` が `/` をまたぐため、実際には効かないパターンがマッチしたように見える。

## 何を書くか

- `paths` で指定したパスの目的や、そこでの作業方針が記述されているか。
- 定型作業を Rakefile や package.json の scripts にまとめている場合、その手順や仕組みを解説していないか。中身はスクリプトに隠蔽されているので、呼び出し方（`rake check` など）を示すだけでよい。解説が要るならスクリプト中のコメントやコミットメッセージに書き、ルールに持ち込まない。
- 対応を見送った内容（検討したが採用しなかった案、今回はやらないと判断したこと）を書いていないか。開発者からの要請が無い限り不要。
- 端的か。冗長な記述や同じ内容の言い換えを重ねていないか。
- このプロジェクト特有の内容だけを説明しているか。言語やフレームワークの一般的な構成は、モデルが既に知っているので触れる必要はない。
