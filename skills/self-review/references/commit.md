# コミットと PR の方針

これからの変更とブランチの未マージのコミットをどう整えるか、そして PR 本文をどう書き、どう反映するかを判断するための方針。

## コミットの整理

- メインブランチに取り込まれていない変更のコミットを、適切な粒度に整える。
- PR には意味のある単位のコミットを含める。
- typo 修正・リファクタリング・テストコード追加などのマイナーな修正は、既存のコミットに amend する。
- 追加方針や方針変更により作業ブランチの内容が大きく変わった場合は、squash して最終的な提出コミットにまとめる。方針変更の過程はコミットに残さない。
- 最終的な提出物が意味的に独立しており、コミットを分割するのが適切な場合にのみ、コミットを追加する。
- **プッシュ済みかどうかは、整理するかどうかの判断材料にしない。** メインブランチに取り込まれるまでは作業中の履歴とみなし、既にプッシュ済みのコミットであっても上記の方針で amend・squash・rebase して整える。プッシュ済みのコミットを整えた場合は `git push --force-with-lease` で更新する。
- 公開 PR 上のレビュー指摘への対応も同様に、原則として対象のコミットに amend/squash して取り込む。「レビュー対応の履歴を残す」ことを理由に別コミットへ分けない（最終的な提出物として意味的に独立している場合を除く）。

## 言語

コミットメッセージおよび PR のタイトル・本文の言語は、CLAUDE.md に指定があればそれに従う。指定がなければ英語で書く。

## 追加テストケースの一覧

- テストケースを追加した場合は、追加したテストケースの一覧を PR 本文に記載する。既存テストケースの内容を修正しただけの場合は、この一覧は不要。
- 目的は追加したテストケースの俯瞰なので、テストケース単位で列挙し、各ケースが何を検証するのかが本文だけで分かるようにする。
- 一覧は Context / Example / 概要（`Description`）の 3 列の表で記載する。テスト対象が複数のファイル・クラスにまたがる場合は、対象ごとに見出しを分けて表を作る。
  - **Context**：`describe` / `context`。入れ子は `>` で連結する。入れ子を持たないフレームワークでは対象のクラス・関数名を書く。
  - **Example**：`example` / `it` やテスト関数。説明を持たないワンライナー（`it { is_expected.to ... }`）は `-` とする。
  - **概要**：そのケースが何を検証するのか。Context と Example の言い換えではなく、そこから読み取れない前提や観点を書く。ただし Example が `-` の行は Context だけで検証内容が読み取れないので、検証内容そのものを書く。
  - Context / Example は列名を英語のままとし、内容もテストコードの記述のまま（訳さない）。3 列目はヘッダー（`概要` / `Description`）も内容も PR 本文の言語に合わせる。

  | Context | Example | 概要 |
  |---|---|---|
  | `#call` > `when the file is missing` | `raises Errno::ENOENT` | 呼び出し側でリトライできるよう、nil や false で握り潰さず例外で失敗させること |
  | `#call` > `when the file is empty` | - | 空ファイルを空配列として返し、例外にしないこと |

- 一覧を載せた PR を更新する際は、追加したテストケースの増減に合わせて一覧を追従させる（テストケースを新たに追加したら追記し、追加していたケースを削除・改名したら該当箇所を修正する）。本文の一覧と実際に追加したテストケースが食い違ったまま残らないようにする。

## PR の作成・更新

self-review は作業ブランチの PR の有無だけ調べ、PR の作成・更新は行わずに該当するケースを呼び出し元へ伝える（レビュー時点では変更が未コミットで、本文に載せる最終形が確定していないため）。また、この時点で PR を作成するのかどうかも self-review からは分からない。

PR を探す際は、作業ブランチに紐づく PR だけに絞り込む。絞り込みが効いていないと無関係な PR が返り、別の PR を書き換えてしまう。呼び出し元が後から探す場合もあるので、この注意も併せて伝える。

- **すでに PR がある場合**：この変更をプッシュする際に、既存の本文を今回の変更に追従させるよう伝える。PR の番号と URL を添える。
  - 本文の更新は全置換になるので、現在の本文を取得し、反映すべき内容（追加テストケースの一覧など）だけを書き換えた全文を渡すことも伝える。ユーザーが書いた記述は消さない。
- **PR が無い場合**：この変更で PR を作成する際に、反映すべき内容を本文に含めるよう伝える。あわせて、ユーザー自らが PR を作成したことを検知した場合も、同じ内容を本文へ反映するよう伝える（プッシュ後にユーザーが PR を作成することがあるため）。
